# Thaki-ValuationProof

**전환사채(CB) 공시·정정공시 사슬에서 평가 기준일에 유효한 조건을 고르고, 평가 Excel 의 입력 셀과 대조해 근거 보고서를 만드는 결정론 도구입니다.**
*Deterministic as-of convertible-bond terms from Korean DART disclosure/correction chains, checked against valuation workbooks, with an evidence report for human review.*

**[Demo (Hugging Face Space, synthetic)](https://huggingface.co/spaces/ThakiCloud/ValuationProof-Demo)** · **[Example reports](examples/synthetic/)** · **[Release audit](RELEASE_AUDIT.md)** · **[License](LICENSE)**

> **이 공개본의 범위.** 코드와 **완전 합성 데이터**만 들어 있습니다. 실제 공시 원문·실제 공시에서 파생한 값·실제 회계사 평가모형은 들어 있지 않습니다.
> 결과는 **회계사가 검토할 후보**이며(승인 상태 `PENDING`), 자동 수정이나 공정가치 계산은 하지 않습니다.

> **V4.2 (2026-11-09).** 공시 기반 감사 엔진의 개선판입니다. **상용 검증을 마친 제품이 아닙니다.** 결과 값은 모두 **공시 기반 추정치**(`DISCLOSURE_BASED_ESTIMATE`)입니다.
> V4.1 공개본은 태그 [`v4.1`](https://github.com/ThakiCloud/thaki-valuationproof/tree/v4.1) 에 그대로 있습니다. 바뀐 점은 [V4.2 절](#v42--전환가액조정-공시-자동-수집과-두-시간축) 을 보세요.

> **꼭 알아 둘 한계 (V4.2).**
> - 계약상 효력일은 확인하지 않았습니다(계약서 없음). 모든 값은 `contract_effective_confirmed = false` 인 공시 기반 추정치입니다.
> - 실제 DART 전체 조건을 **완전 감사한다고 주장하지 않습니다.** 공시에서 기계적으로 읽히는 필드만 다룹니다.
> - "표시 없이 틀린 값 0건"은 **평가한 공시 기반 표본(60개사·102사슬)과 두 해석(IA·IB) 범위 안의 결과**입니다. 정확도 100% 가 아닙니다.
>   정답도 같은 수집 공시에서 만든 것이라 **독립 정답 대조가 아닙니다.** 불확실한 값은 `확인 필요` 로 돌려서 얻은 결과입니다.
> - 그 대가로 **분기말 (사슬×분기말) 쌍의 35.3%**(200/567)가 사람 확인으로 갑니다(V4.1 은 같은 계산으로 23.6%).
> - 조정 공시 [기재정정]의 정정전/정정후 표 형식은 아직 읽지 못합니다(C6). 회차 중복 검사(C4)는 수집한 사슬끼리만 봅니다.
> - **실제 회계사 Excel 로는 평가하지 않았습니다.** 고객 실증도 없습니다.

## 무엇을 하나

| 단계 | 모듈 | 하는 일 |
|---|---|---|
| ① 공시 사슬 추적 | `dart_change` · `change_v3` · `dart_source` | 원공시(전환사채권발행결정)와 기재정정 공시를 한 발행 사슬로 묶고, 버전마다 조건 값을 서식에서 뽑습니다 |
| ② 기준일 조건 선택 | `asof_terms` | 버전마다 **효력일**(공시에 적힌 이사회결의일·조정가액 적용일, 없으면 접수일 + `date_key_fallback = true`)을 키로 기준일 T 에 유효한 버전을 고릅니다. T 뒤 버전은 제외 목록에 남기고, 값마다 근거(접수번호·원문 줄·문자 구간·sha256·날짜 키)를 답니다 |
| ③ Excel 대조 | `excel_v3` · `audit_v4` | 평가 Excel(읽기 전용)에서 전환가액·리픽싱 하한·만기·표면/만기이자율·납입일·전환청구기간·풋/콜 셀을 찾아 기준일 값과 비교합니다 |
| ④ 근거 보고서 | `audit_v4.write_reports` | JSON·Markdown·HTML. 오류 후보마다 **셀 주소 + Excel 값 + 공시 값 + 근거 공시 + 사람 승인 필드** |
| (참고) RCPS | `rcps` | 비상장 RCPS 입력 스키마와 검토 체크리스트만. 상태는 항상 `CUSTOMER_EVIDENCE_REQUIRED`, 판정 없음 |

분류: `일치` · `불일치`(값 다름 / 정정 미반영 / 기준일 뒤 정정 선반영) · `누락` · `미확인`(사람 검토) · `해당없음` · **`확인 필요(효력일 미확정)`** · **`확인 필요(조정 공시 수집 미검증)`**(V4.2).

V4.2 모듈: `adjust_events` — 발행사별 `전환가액의조정` · `전환가액ㆍ신주인수권행사가액ㆍ교환가액의조정(안내공시)` 공시 목록·원문 수집, 회차 연결, [기재정정] 개정 이력, 수집 완전성 기록.

### 안전 규칙 (코드와 테스트로 고정)

- **날짜 키 = 공시에 적힌 효력일.** 이사회결의일(결정일)·조정가액 적용일이 공시에 있으면 그 날짜, 없으면 접수일을 쓰고 `date_key_fallback = true` 로 표시합니다.
- **효력일이 확정되지 않아 값이 갈리면 자동 판정하지 않습니다.** 기준일이 결의일과 접수일 사이이거나, 기준일 뒤에 접수된 *기재 정정*(소급인지 장래인지 공시로 알 수 없음)이 값을 바꾸면
  그 필드는 `effective_status = UNCONFIRMED_DEPENDS`, 분류 **`확인 필요(효력일 미확정)` / needs review** 가 됩니다. 후보 값(`alternative_values`)을 함께 내고,
  규칙이 냈을 일치/불일치는 `blocked_auto_class` 로만 남기며 `approval_required = true`, `auto_verdict_allowed = false` 입니다.
- 계약상 효력일은 계약서로 확인하지 않았으므로 모든 값에 `contract_effective_confirmed = false` 를 답니다. 공시 ≠ 서명 계약.
- 기준일이 원 결의일보다 앞서면 조건을 내지 않습니다(`NOT_YET_FILED`). 추측하지 않습니다.
- 규칙 신호로만 이어 붙인 정정(사람 미검수)은 `link_review_required = true`.
- 사전에 없는 라벨·전치 표에서 회차를 못 읽은 경우는 `누락` 으로 확정하지 않고 `미확인` 으로 보냅니다(오탐 확정 방지).
- Excel 은 수정하지 않습니다(감사 전후 sha256 동일 확인). 수정 제안은 `requires_approval = true`, `auto_applied = false`.
- 풋·콜은 "있다/없다 + 최초 날짜 후보"만 냅니다. 행사가·비율 등 세부는 해석하지 않고 항상 사람 확인입니다.
- (V4.2) **조정 공시 수집이 완전한지 확인하지 못하면 전환가액을 자동 확정하지 않습니다.** 검사 C1~C7 중 하나라도 실패하면(또는 수집을 안 했으면 C0)
  전환가액은 `coverage_status = EVENT_COVERAGE_UNVERIFIED`, 분류 **`확인 필요(조정 공시 수집 미검증)`**, `auto_verdict_allowed = false`, 실패 사유 목록을 함께 냅니다.
- (V4.2) **평가 기준일(`valuation_asof`)과 지식 시점(`knowledge_cutoff`)을 나눕니다.** 사건마다 `rcept_dt`(접수일)·`effective_at`(공시에 적힌 조정가액 적용일)·`known_at`(공개된 날,
  정정으로 바뀐 값은 그 정정 접수일)을 남기고, 값마다 어느 모드로 계산했는지(`mode`) 적습니다.

## V4.2 — 전환가액조정 공시 자동 수집과 두 시간축

V4.1 은 호출자가 `chain["adjustments"]` 를 넣어야만 리픽싱(전환가액 조정)을 반영했습니다. V4.2 는 CLI 기본 경로(`--adjustments live`)에서 발행사의 조정 공시를 직접 수집합니다.

| 항목 | 내용 |
|---|---|
| 수집 | 발행사별 OpenDART `list.json`(공시유형 전체, 2년 창, 마지막 쪽까지) → 보고서명 필터 → 원문 → 결정론 셀 규칙 파서(LLM 없음). EUC-KR 원문은 CP949 로 다시 읽습니다 |
| 사건 | `rcept_no` · 보고서명 · DART 링크 · `rcept_dt` · `effective_at`(못 읽으면 접수일 + `effective_fallback = true`) · `known_at` · 조정전/조정후 가액 · 회차 매칭 근거 · [기재정정] 개정 이력 |
| 모드 | `restated` = 수집 종료일까지 알려진 사건 전부를 효력일로 적용 · `as_known` = `known_at <= knowledge_cutoff`(기본 = 기준일)인 사건만 |
| 완전성 검사 | C1 목록 응답·쪽 수·건수 일치 · C2 목록 창이 [사슬 시작, 지식 시점] 을 덮음 · C3 대상 공시 전부 판독(또는 다른 회차로 명시) · C4 회차가 있고 같은 회사에 같은 회차 사슬이 둘이 아님 · C5 다음 조정의 조정전 가액 = 계산 가격 · C6 [기재정정]이 모두 원 조정에 연결 · C7 같은 회차·적용일에 값 충돌 없음 |
| 실패 시 | 전환가액 = `EVENT_COVERAGE_UNVERIFIED` + 사유. 다른 필드는 막지 않습니다 |
| V4.1 재현 | `--engine 4.1` (조정 수집·완전성 검사 없음). 합성 데모 4종 워크북 대조는 V4.1 엔진 그대로입니다 |
| 버그 수정 | V4.1 공개본에 적어 둔 3건: HTML 보고서의 `확인 필요` 색상 KeyError · 원 결의일을 다시 적은 정정이 효력일 정렬에서 앞 버전으로 취급되던 문제 · `확인 필요` 행의 공시 값 열이 접수일 기준 값으로 찍히던 문제 |

합성 시연(키·네트워크 불필요). 가상 조정 공시 A1(접수 2025-11-21, 적용일 2025-11-20, 8,500 → 7,800)과 그 [기재정정] A1′(접수 2025-12-05, 7,750)을
내장한 가짜 OpenDART 목록·원문 소스로 실제 수집기(`adjust_events.collect_corp`)를 그대로 돌립니다.

```bash
valuationproof terms --synthetic --asof 2025-11-20                          # restated 7750 · as_known 8500
valuationproof terms --synthetic --asof 2025-11-20 --mode as-known --knowledge-cutoff 2025-11-30   # 7800
valuationproof terms --synthetic --asof 2025-11-20 --adjustments off --mode restated              # EVENT_COVERAGE_UNVERIFIED (C0)
```

| 시나리오 (기준일 2025-11-20) | 전환가액 | 수집 검사 |
|---|---|---|
| restated (2026-01-31 까지 알려진 사건 전부) | 7,750 (A1 + 정정 A1′) | VERIFIED |
| as_known, 지식 시점 = 기준일 | 8,500 (A1 은 아직 공개 전) | VERIFIED |
| as_known, 지식 시점 2025-11-30 | 7,800 (A1 공개, 정정 전) | VERIFIED |
| 목록 요청 실패 | 8,500 후보, 자동 확정 안 함 | `EVENT_COVERAGE_UNVERIFIED` (C1) |
| 수집 끔 (`--adjustments off`) | 8,500 후보, 자동 확정 안 함 | `EVENT_COVERAGE_UNVERIFIED` (C0) |

미리 만든 결과: [`examples/synthetic/v42_synthetic_demo.json`](examples/synthetic/v42_synthetic_demo.json), [`examples/synthetic/v42_terms_2025-11-20.json`](examples/synthetic/v42_terms_2025-11-20.json).

#### 지표와 분모 (무엇을 센 것인지)

모든 비율의 기본 단위는 **(사슬, 분기말 기준일 T) 쌍**입니다. S_all 분기말 쌍 = **567**(102사슬 전부 `RESOLVED`). 공시 건수나 회사 수가 아닙니다.

| 지표 | 값 | 분자 / 분모 | 모집단·단위 | 겹침 |
|---|---|---|---|---|
| 전환가액 자동 확정 | **78.8%** | 447 / 567 | S_all 분기말 쌍. 전환가액 필드가 `UNCONFIRMED_DEPENDS` 도 `EVENT_COVERAGE_UNVERIFIED` 도 아님 | 아래 두 행과 서로 겹치지 않음 |
| 전환가액 `EVENT_COVERAGE_UNVERIFIED` | **12.2%** | 69 / 567 | 같은 쌍. 수집 완전성 검사 실패 | 아래 행과 겹침 0 (447+69+51=567 에서 계산) |
| 전환가액 `확인 필요(효력일 미확정)` | 9.0% | 51 / 567 | 같은 쌍. 효력일이 공시로 확정 안 돼 값이 갈림 | 위 행과 겹침 0 |
| 검토 전환율 (M2) | **35.3%** | 200 / 567 | 같은 쌍. 필드 하나 이상이 사람 확인(`UNCONFIRMED_DEPENDS` 또는 `EVENT_COVERAGE_UNVERIFIED`) | 위의 전환가액 표시 120쌍(69+51)을 **모두 포함**. 나머지 80쌍은 다른 필드만 효력일 미확정 |
| 필드 자동 판정 (M1) | 86.3% | 3,426 / 3,969 | (쌍 × 서식 필드 7개) | — |
| C6 정정 연결 실패 | 52 | 사유 항목 수 | 전환가액이 미검증인 분기말 쌍에 붙은 사유 항목. **한 쌍에 여러 개** 붙을 수 있음(정정 공시마다 1개) → 서로 다른 쌍 수는 미확인(계산상 30~52) | C4·C5 와 겹칠 수 있음, 쌍 단위 겹침은 미확인 |
| C4 회차 모호 | 22 | 쌍 수 | 사슬당 C4 사유는 최대 1개라 22 = 서로 다른 쌍 수 | 위와 같음 |
| C5 가격 연속성 불일치 | 17 | 쌍 수 | 쌍당 C5 사유는 최대 1개(바로 다음 조정만 검사)라 17 = 서로 다른 쌍 수 | 위와 같음 |
| 표시 없는 오답 | **0** | 0 / 4,536 (분기말) · 0 / 508,528 (매일) | (쌍 × 8칸: 서식 필드 7 + status), V4.2 restated, 정답 IA_full·IB_full 각각 | — |

- **합계가 100% 가 아닌 이유.** 78.8%·12.2%·9.0% 는 **전환가액 한 필드**를 셋으로 나눈 것이라 더하면 100% 입니다. 35.3% 는 **필드 아무거나 하나라도** 사람 확인인 쌍의 비율이라 단위가 다르고,
  전환가액 표시 쌍(21.2%)을 포함합니다. C4·C5·C6 는 비율이 아니라 사유 건수이고 한 쌍에 여러 사유가 붙으므로 합 91 이 미검증 쌍 69 보다 큽니다.
- C1·C2·C3·C7 사유는 최종 측정에서 0건입니다. 수집된 조정 [기재정정] 공시는 8건이며 그중 3건이 표를 읽지 못했습니다(행 없음 1·머리글 인식 실패 2). C6 52건이 이 3건에서 몇 건씩 나왔는지는 집계에 없습니다(미확인).
- 표시 없는 오답 0 은 값이 정답과 다를 때 **전부 표시했다**는 뜻입니다. 같은 분기말 4,536칸에서 소급 해석(IB_full)과 값이 다른 칸은 455칸이고, 그 455칸은 모두 `확인 필요` 로 표시됐습니다.
  정답 IA_full·IB_full 은 V4.2 가 수집한 같은 조정 공시와 같은 효력일 규칙으로 만든 것이므로, G1 은 "수집한 사건을 빠짐없이 반영하거나 표시했다"는 확인이지 독립 정답 대조가 아닙니다. `as_known` 모드는 G1 대상이 아닙니다.

## 실제 공시 모드 (선택, 본인 API 키 필요)

실제 공시는 이 레포에 들어 있지 않습니다. 공시는 [DART 전자공시시스템](https://dart.fss.or.kr) 에서 보고,
조회는 [OpenDART](https://opendart.fss.or.kr) 에서 **본인이 발급받은 인증키**로 합니다.

```bash
export API_K_DART=<your OpenDART key>            # 키는 환경변수에서만 읽고 출력·저장하지 않습니다
valuationproof audit --data ./dart_data --fetch --corp <8자리 corp_code> --cb <원공시 또는 정정 접수번호> \
                     --asof 2025-12-31 --excel my_model.xlsx --out out/
```

- `--fetch` 는 발행사 1곳의 CB 발행결정(정정 포함) 목록과 원문만 소량 조회해 `--data` 디렉터리에 저장합니다(호출 수를 출력).
- (V4.2) `audit`·`resolve`·`terms` 는 기본으로(`--adjustments live`) 같은 발행사의 전환가액조정 공시 목록·원문을 조회해 `--event-cache`(기본 `<data>/adjust_cache`)에 캐시합니다.
  키가 없거나 목록 한 쪽이라도 실패하면 전환가액은 `EVENT_COVERAGE_UNVERIFIED` 로 나오고 자동 확정되지 않습니다. 네트워크 없이 쓰려면 `--adjustments cache` 또는 `off`.
- 받은 공시 원문·파생물은 **본인 환경에만** 두세요. 이 프로젝트는 공시 원문이나 그 파생 데이터를 재배포하지 않으며, 사용자에게도 권하지 않습니다.
- 외부 API 의존성은 **OpenDART(선택)** 하나뿐입니다. LLM·상용 API 는 쓰지 않습니다.
- 한계: 조정 [기재정정]의 정정전/정정후 표 형식은 아직 파싱하지 못해 C6 로 `확인 필요` 가 됩니다. C4 는 수집한 사슬끼리만 회차 중복을 봅니다(데이터셋 밖 같은 회차 발행은 못 봄).

## 검증된 것 / 검증되지 않은 것 (Validated / Not validated)

### 검증된 것 — 공개 DART 필드 + 합성 워크북

내부 개발 단계에서 OpenDART 공개 공시(CB 발행결정·기재정정)로 측정한 값입니다. 측정에 쓴 공시 원문·파생 데이터는 이 레포에 없고 집계 수치만 옮깁니다.

| 항목 | dev (사슬 549, 2026년 전 원공시) | test (사슬 412, 2026년 원공시, 1회 보고) |
|---|---|---|
| 기준일 조건 선택 정확도 (약한 정답 기준, 필드 micro) | **1.0** (4,050 필드) | **0.9997** (3,394 필드) |
| 정정 무시(원공시 값만) 기준선 | 0.819 | 0.8751 |
| 정정으로 값이 바뀐 필드만 | 1.0 vs 기준선 0.0 (733) | 1.0 vs 기준선 0.0 (423) |
| 시점 규칙 위반(기준일 뒤 값 유입) | 0 / 816 검사 | 0 / 390 검사 |

위 표는 V4.0(접수일 키) 규칙으로 잰 값입니다(내부 원장 `D_valuationproof_v4_1108`). 효력일 키(V4.1) 관련 수치는 아래 별도 표이며 내부 원장 `D_effective_date_1109` 에서만 옮겼습니다.

- **약한 정답(weak gold)** 입니다: 정답은 같은 공시 출처의 최신 구조화 레코드이고, 중간 버전 정답은 없으며, 독립 전문가 검증이 아닙니다. test 의 오차 1건(납입일)은 정책상 고치지 않았습니다.
- 합성 워크북: 4종 데모 기대 결과 전부 충족, 오류 확정 오탐 0. 사전 밖 동의어 합성 어휘에서 이전 버전(V3) 오경보 0.98 → V4 오류 확정 0.0(대신 `미확인` 0.364).
  전치 표 회차 읽기 정확도 합성 사후 점검 0.2026 → 1.0.

#### 효력일(V4.1) — 공개 DART 필드 검증, 계약서 검증 아님

표본: 공개 공시 60개사(대부분 2025~2026 접수). 시장 전체 비율로 일반화하지 않습니다. 효력일 = 발행사가 공시에 적은 이사회결의일·조정가액 적용일입니다.

| 측정 | 값 |
|---|---|
| 원공시 결의일 ≠ 접수일 | 19 / 92 (0.2065) |
| 전환가액 조정 적용일 ≠ 접수일 | 31 / 114 (0.2719) |
| 효력일이 접수일보다 *뒤*인 사건 | 0 — 전부 "효력이 먼저, 공시가 나중" |
| 분기말 기준 선택이 바뀌는 비율(날짜 키만): 정정 장래 해석 IA / 소급 해석 IB | 0.0035 / 0.2363 |
| 매일×필드 508,528쌍에서 표시 없이 틀린 값: V4.0 → V4.1 (IB 대비) | 108,835 → **0** (달라지는 값은 전부 `확인 필요` 로 표시) |

| 리픽싱 회차에서 조정 공시를 안 넣었을 때 분기말 전환가액이 낡은 비율 (V4.0) | 84 / 136 (0.6176) — V4.1 은 `chain["adjustments"]` 로만 해소, V4.2 는 자동 수집(위 R84 절) |

### 검증되지 않은 것

- **실제 회계사 평가 Excel** — 실 평가모형으로 정확도를 잰 적이 없습니다. 합성 워크북 결과를 실무 정확도로 읽지 마세요.
- **계약서 원문** — 공시 ≠ 서명 계약. 계약상 효력일·기재 정정의 소급 여부는 확인하지 않습니다(`contract_effective_confirmed = false`).
- **조정 공시 수집의 완전성** — 검사 C1~C7 은 수집 기록 안에서의 일관성 검사입니다. DART 에 조정 공시 자체가 누락·지연 공시된 경우는 알 수 없습니다. 조정 [기재정정] 정정표 파싱(C6)은 미구현입니다.
- **자동 공정가치·DART 조건 전수 감사** — 하지 않습니다. 결과는 공시 기반 추정치입니다.
- (V4.2 에서 수정됨) V4.1 공개본에 적었던 `확인 필요` 행 공시 값 표시 불일치와 원 결의일을 다시 적은 정정의 정렬 문제는 V4.2 에서 고쳤고 회귀 테스트(`tests/test_v42_events.py`)로 고정했습니다.
- **비상장 RCPS** — 스키마·체크리스트만 있고 추출·판정은 없습니다.
- **공정가치** — 공정가치를 계산하거나 검증하지 않습니다.
- 고객 실증(customer validation)을 거친 적이 없습니다.
